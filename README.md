# Performance test kit (k6 + Kubernetes)

Load-test an API that runs as a container in Kubernetes, with k6 running as a Job
inside the same cluster.

## Is this a sensible design?

Yes - running the generator inside the cluster is the standard pattern (it is what
the official `grafana/k6-operator` does), and it exists for a good reason: you stop
measuring your laptop, your home network and your VPN, and start measuring the
system. But the pattern only pays off if three things are true, and the original
version of this kit violated all three:

1. **The generator must not be the bottleneck.** k6 needs real CPU, and it should
   not share a node with the system under test. A CPU-throttled k6 reports the API
   as slow when k6 is what ran out of CPU.
2. **You must measure the configuration you ship.** A Debug build, a Development
   environment, or a Swagger page tells you nothing about production.
3. **Numbers must be kept and compared.** A single run answers nothing on its own;
   "is this release slower than the last one?" needs a recorded baseline.

## Two paths, one set of scenarios

| | `k6/run-test.ps1` | `scripts/deploy-and-test.ps1` |
|---|---|---|
| Where k6 runs | docker compose, on your machine | a Kubernetes Job, in the cluster |
| Use it for | writing and debugging scenarios; "does the script work" | every number you intend to act on |
| Target must be | reachable from a container (`host.docker.internal`, not `localhost`) | in-cluster DNS (`http://api-service:8080/...`) |
| Observability | Grafana + Prometheus via compose (k6 remote-writes into Prometheus) | `results/<run>/` artefacts (see below) |

Both write `results/<timestamp>-<type>/{k6.log,summary.json,meta.json}`, so a local
run and a cluster run are compared the same way.

```
k6/scripts/            scenarios (smoke, load, stress, soak, spike)
k6/scripts/lib/        shared env handling + the machine-readable summary
k6/tests/              node-runnable check of the summary library
k8s/base/              namespace-free manifests: Deployment, Service (kustomize)
k8s/overlays/local/    the single-node local overlay
k8s/.generated/        per-run overlays, regenerated by the runner (gitignored)
scripts/               the Kubernetes runner, the baseline gate, cleanup
results/               run artefacts (gitignored - these are evidence, not source)
baselines/             the accepted numbers a run is compared against
```

## Quick start

Prerequisites: Docker, `kubectl` pointed at a cluster, PowerShell 7+ (`pwsh`) for
the runners, and Node only if you want to run the library test.

```powershell
# 1. A smoke test first, always. If this fails, nothing after it means anything.
pwsh -File scripts/deploy-and-test.ps1 `
  -TargetUrl http://api-service:8080/api/health `
  -TestType smoke

# 2. A load test with your own knobs, reusing the deployment that is already up.
pwsh -File scripts/deploy-and-test.ps1 `
  -TargetUrl http://api-service:8080/api/orders `
  -TestType load -TestOnly `
  -EnvVars TARGET_VUS=200,HOLD_DURATION=15m

# 3. Accept the result as the baseline, then gate later runs against it.
pwsh -File scripts/compare-summary.ps1 -Current results/latest.txt -Baseline baselines/load.json -Update
pwsh -File scripts/compare-summary.ps1 -Current results/latest.txt -Baseline baselines/load.json

# 4. Tear everything down (results/ is left alone).
bash scripts/cleanup.sh
```

Local authoring, no cluster:

```powershell
pwsh -File k6/run-test.ps1 -TargetUrl http://host.docker.internal:5000/api/health -TestType smoke
```

### Getting local images into the cluster

`-Image` defaults to `exchangeportal-finance-api:local`, built locally, which only
works if the cluster can see it. The runner handles this where it can:

| Cluster | Behaviour |
|---|---|
| Docker Desktop Kubernetes | Shares the Docker daemon: nothing to do. |
| kind | The runner detects a `kind-*` context and runs `kind load docker-image` for each locally-built image. |
| minikube | Same, via `minikube image load`. |
| Anything remote | Push to a registry the cluster can reach, and pass a real tag or digest: `-Image registry/api@sha256:...` |

Prefer an image your application's CI built and published. `-ApiPath` still exists
for building from source, but it encodes another repository's directory layout and
is scheduled for removal (P1 item 8 below).

## Golden rules

- **The measured configuration is the experiment.** `k8s/base/api-deployment.yaml`
  runs `Production`, the image must be a Release build, and the CPU/memory
  requests and limits are part of the result. Change any of them and earlier runs
  are no longer comparable - record it as a new baseline.
- **Test a real endpoint.** A Swagger page is static HTML served by middleware that
  is normally disabled outside Development. The runner warns if your `-TargetUrl`
  contains `swagger`; that warning is the ghost of a bug (see P0 item 1).
- **Isolate the generator.** The k6 pod prefers a node without the API on it and
  requests `1` CPU with no CPU limit. On a single-node cluster that anti-affinity
  is ignored and the two compete for CPU - one more reason local numbers are only
  for script validity.
- **Keep the evidence.** Never overwrite `results/`; the runner creates a new
  directory per run and `results/latest.txt` points at the newest.
- **Stress and spike tests are supposed to fail their thresholds.** k6 exits `99`
  when a threshold is crossed. For those two types, a non-zero exit is the finding,
  not a broken build - which is why they are run by hand, not on every commit.

## Which test, and where

| Test | Question it answers | Profile | Home environment | Cadence |
|---|---|---|---|---|
| **smoke** | Does the script and target work at all? | 1-2 VUs, <1 min | laptop, PR pipeline, production synthetic monitor | every change |
| **load** | Do we still meet the SLO at expected peak? | ramp, hold at peak, ramp down | staging (prod-shaped) | per release |
| **stress** | Where is the knee, and does it degrade gracefully? | stepped plateaus to and past failure | staging only | per major release |
| **spike** | Can it absorb a flash crowd, and how fast does it recover? | baseline -> sharp spike -> baseline | staging, before known traffic events | occasional |
| **soak** | Does anything leak, fill up, or drift over hours? | 2-24h at 60-80% of peak | dedicated staging, overnight | nightly/weekly |

### Local, staging, or production?

- **Your laptop** - write and debug scenarios here. Never take capacity numbers
  from it: the generator and the target share one machine, the Docker VM adds a
  hop, and a laptop holds neither a steady clock nor a steady thermal budget.
- **CI (ephemeral kind/minikube)** - smoke on every pull request, plus optionally a
  short load run with tight thresholds. Cheap, isolated, deterministic. Keep it
  under about five minutes or people will route around it.
- **A dedicated, prod-shaped staging cluster** - the default home for load, stress,
  spike and soak. Same instance sizes, same replica count, same configuration and
  **production-sized data**; nothing else running on it; reset between runs. Data
  volume is the single biggest realism factor for a database-backed API.
- **Production** - only low-rate synthetic monitoring of a real endpoint, or (rarely,
  with approval) a read-only canary load with a slow ramp, SLO-based auto-abort, a
  change freeze and on-call informed. Never stress-to-destruction, never
  spike-to-failure, never a soak, and never load from production against shared
  databases, third parties or payment gateways.

Production is the most realistic environment and the least destructible one; that
trade-off is exactly why prod-shaped staging exists.

## Scenario knobs

Pass with `-EnvVars NAME=value,NAME=value`. `TARGET_URL` cannot be set this way: use
`-TargetUrl`, which is validated and recorded.

| Knob | Default | Applies to |
|---|---|---|
| `TARGET_URL` | *(required, no default)* | all |
| `REQUEST_PAUSE` | 0.5 / 0.3 / 0.2 s | all (think time between iterations) |
| `TARGET_VUS` | 1 / 50 / 20 | smoke / load / soak |
| `TEST_DURATION` | 1m | smoke |
| `RAMP_DURATION` | 1m / 2m | load / soak |
| `HOLD_DURATION` | 10m / 2h | load / soak |
| `STEP_VUS` | 50 | stress (VUs added per plateau) |
| `STRESS_STEPS` | 4 | stress (peak = `STEP_VUS` x steps) |
| `STEP_DURATION` | 2m | stress |
| `BASELINE_VUS` | 10 | spike |
| `SPIKE_VUS` | 100 | spike |
| `BASELINE_DURATION` | 30s | spike (also the recovery window) |
| `SPIKE_DURATION` | 1m | spike |

Thresholds live in the scenario files, next to the profile they belong to.

## Results, baselines and gating

Every run gets `results/<utc timestamp>-<type>/`:

| File | What it is |
|---|---|
| `k6.log` | the full container log, including the human-readable summary |
| `summary.json` | machine-readable summary, schema `perftest.summary/v1` |
| `meta.json` | target URL, image, git revision, env knobs, pod, k6 exit code |
| `k6-job.yaml` | the exact Job manifest that was applied (cluster runs) |

The summary travels through the log between two markers, which is why it works
identically for compose and for a Job - no shared volume, no sidecar, no object
storage, and nothing to collect from a container that has already exited.

`scripts/compare-summary.ps1` compares a run against `baselines/<type>.json` and
exits non-zero when p95/p99/avg latency, TTFB, error rate or throughput regresses
beyond `-TolerancePercent` (default 10%). Improvements always pass. Recording a
baseline from a run whose thresholds failed is refused.

Do not set the tolerance to 1% and expect a stable gate: run-to-run variance on
real infrastructure is bigger than that, and a gate that cries wolf gets ignored.

## Did the generator limit the result?

This is the first question to ask about any surprising number. The runner gives you
some of it, but the check is manual:

1. **CPU:** `kubectl top pod -n perf-test -l job-name=k6-test-load`. If the k6 pod
   is pinned near its request while the API pod is idle, suspect the generator.
   (Needs metrics-server.)
2. **Node placement:** `kubectl get pod -o wide` - if k6 and the API are on the same
   node in a single-node cluster, you are measuring contention.
3. **Sanity run:** point the same scenario at a trivially fast endpoint in the same
   cluster and compare the achieved `http_reqs.rate`. If it is close to your real
   run's RPS, you found the generator's ceiling, not the API's.
4. **Little's Law:** `VUs ~= RPS x latency`. If the numbers disagree by an order of
   magnitude, one of the three is not what you think it is.

## Verification status

Two flags exist specifically so the runner can be checked without a cluster:
`-EmitJobManifest` (write the Job manifest and exit) and `-FromLog` (re-parse an
already-collected log, which exercises summary extraction, `summary.json` and
`meta.json`).

```powershell
node k6/tests/summary.test.mjs                       # summary library, all assertions
kubectl kustomize k8s/overlays/local                 # base + overlay render cleanly
pwsh -File scripts/deploy-and-test.ps1 -TargetUrl http://api-service:8080/api/orders -TestType load -EmitJobManifest ./job.yaml
pwsh -File scripts/deploy-and-test.ps1 -TargetUrl http://api-service:8080/api/health -TestType smoke -FromLog results/<run>/k6.log
```

Verified (no cluster, no Docker daemon required): the summary library against
synthetic k6 payloads; the result path end to end, including exit code 99 on a
crossed threshold; test-type validation; the baseline gate on pass / regression /
missing-metric / failing-baseline cases; `kubectl kustomize` for the base, the
checked-in overlay and a generated per-run overlay (including digest pinning,
namespace override, replicas and environment); the generated Job manifest parses as
a Kubernetes object.

**Not verified here** - no Docker daemon and no reachable cluster in the environment
where these changes were made: `docker build`, the real `kubectl apply -k` against a
cluster, the rollout, and a Job actually running. The shell wrappers' syntax is also
unverified (the sandbox blocked bash). Verify in this order:

```powershell
docker build -f k6/Dockerfile -t k6-custom:local .     # generator image builds
kubectl apply -k k8s/overlays/local --dry-run=server   # cluster-side validation
pwsh -File scripts/deploy-and-test.ps1 -TargetUrl http://api-service:8080/api/health -TestType smoke
```

## Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| k6 pod `Pending`, "cannot be scheduled" | Not enough CPU for the request. Lower `-K6CpuRequest`, or free capacity. |
| k6 pod `ImagePullBackOff` | The image is not visible to the cluster: `kind load docker-image` / `minikube image load` / push to a registry. |
| "k6 output contained no summary block" | The container failed before the end-of-test summary. Read `k6.log` or `kubectl logs -n perf-test -l job-name=...`. |
| Every response is 404 | Wrong path, or the wrong port (the Service is 8080 end to end), or the app runs with an environment where the route is not registered. |
| Latency is flat and suspiciously good | You are probably not load-testing the app: check what the endpoint actually does. |
| Exit code 99 | Thresholds crossed - a real finding. Expected for stress and spike. |
| Local run cannot resolve the target | The runner now **rejects** a `localhost`/`127.0.0.1` target instead of warning: inside the container that is the container itself, and every request fails in ~2ms. Use `host.docker.internal`, or `-AllowLocalhostTarget` if you truly mean the k6 container. |
| Local run works but Grafana shows no data | Three things must all hold: k6 has an output enabled (`K6_OUT`, not just `K6_PROMETHEUS_RW_SERVER_URL` - the URL alone sends nothing), Prometheus accepts remote writes (`--web.enable-remote-write-receiver`), and Grafana has a provisioned datasource (an empty `grafana/provisioning/` means none). Check <http://localhost:9090/graph> first - see `k6/README.md`. |

## What changed (P0: making the numbers trustworthy)

1. **Targeted a real endpoint.** The old default was
   `http://api-service:8080/swagger/index.html` - a static Swagger page, on a
   container running `ASPNETCORE_ENVIRONMENT=Production` where Swagger is normally
   not registered. `-TargetUrl` is now mandatory and validated.
2. **Stopped measuring a Debug build.** The build arg was `ENVIRONMENT=Development`
   while the container ran as `Production`. `-BuildEnv` now defaults to `Release`
   and warns loudly on `Development`.
3. **Fail fast instead of hanging.** `kubectl wait --for=condition=complete` never
   returns early when k6 exits `99`, so a failing test blocked for the full 30
   minute timeout. The runner now waits for complete *or* failed, reports k6's own
   exit code, and short-circuits on `ImagePullBackOff` and unschedulable pods.
4. **Replaced the `kubectl patch` hack with kustomize.** Strategic-merge patches on
   `containers` and Service `ports` *add* entries rather than replacing them: the
   Service ended up advertising a port 80 route with nothing listening behind it,
   which is exactly why the scripts' `http://api-service/` default could never work.
5. **Added readiness and liveness probes.** Without them `rollout status` goes green
   the moment the container is running, so the test could start before Kestrel was
   listening.
6. **Kept the evidence.** Log, machine-readable summary, metadata and the applied
   Job manifest are written to `results/`, and `compare-summary.ps1` turns that into
   a release gate against a recorded baseline.
7. **Protected the generator.** The k6 pod requests real CPU, has no CPU limit, and
   prefers a node without the API on it.
8. **Removed the silent traps.** A `-TestType` with no scenario file now lists the
   real options (this is how `-TestType load` used to be accepted with no
   `load-test.js`); `checks` has a threshold so a failing assertion fails the run;
   response bodies are discarded so the generator's memory is not under test; the k6
   image tag is pinned.

## Not done yet (P1/P2, in the order I would take them)

1. **Open-model load.** `load-test.js` still uses VU-based stages, which is a
   *closed* model: offered load falls when the API slows down, so the test backs off
   exactly when you want to see the system buckle. Move load/stress/spike to
   `constant-arrival-rate` / `ramping-arrival-rate`.
2. **A real user journey.** One GET is not a workload. Add authentication, a
   read/write mix, realistic payloads, and `setup()`/`teardown()` for test data.
3. **Observability for the system under test.** k6 alone shows latency, not cause.
   Add `kube-state-metrics`, node-exporter and .NET runtime metrics (OpenTelemetry or
   `dotnet-counters`), then put node/pod CPU and memory on the same dashboard as the
   k6 latency panel.
4. **A metrics sink for cluster runs.** Cluster Jobs report via artefacts and logs
   only. The local compose stack now sends k6 metrics to Prometheus by remote write
   (`k6/docker-compose.yml`, `k6/grafana/`); point cluster runs at a Prometheus you
   keep - the same remote-write output works from inside a cluster, it just needs a
   reachable URL and `K6_OUT` set on the Job.
5. **Decouple from the application repository.** Consume a pinned image digest and
   delete the `-ApiPath` build path, the `..\..\..` context guess and the
   `nuget.config` temp-Dockerfile rewrite.
6. **CI.** Smoke on every pull request on ephemeral kind; nightly load and soak in
   staging; stress and spike by hand with approval; publish artefacts and trends.
7. **k6-operator and distributed load.** Replace the hand-rolled Job with a
   `TestRun` resource when a single generator caps out, and add chaos/HPA-validation
   scenarios.
8. **Decide the fate of the two InfluxDB-era dashboards** in `k6/dashboards/`. They
   contain InfluxQL queries against a `k6influxdb` datasource and cannot work against
   Prometheus; they are no longer mounted. `14801_rev2.json` is additionally broken
   even for InfluxDB, because it uses `${DS_DUMMY}`, an import-time placeholder that
   file provisioning does not resolve.
9. **Align the generator version.** `k6/Dockerfile` pins k6 1.3.0 for cluster runs
   while `docker-compose.yml` pins 0.54.0 locally (and the remote-write output name
   differs between those lines). A different generator version is a different
   experiment.

## Rules worth writing on the wall

Never load-test production to destruction. Never run a load test from a laptop and
call it a capacity number. Never compare two runs whose configuration changed. Never
record a baseline from a run whose thresholds failed. And always smoke first.
